# `/load-context` — стандартная загрузка контекста проекта

AI-агент **обязан** запустить этот workflow при старте любой нетривиальной задачи. Цель: за минимум токенов получить достаточный контекст, чтобы не повторить уже сделанные ошибки и соблюдать архитектурные инварианты.

## Шаги

1. Прочитать `AGENTS.md` — точка входа, роли, дисциплина.
2. Прочитать `docs/ARCHITECTURE_INVARIANTS.md` — жёсткие правила. Если задача затрагивает любую listed-область, **активно проверять** что предложение не нарушает инвариант.
3. Сделать `grep` по `docs/DECISIONS.md` по ключевым словам задачи (имя сервиса, имя файла, тема). Если есть запись с `Status: accepted` — она **обязательна** к учёту.
4. Если задача затрагивает конкретный backend-сервис, прочитать `backend/<service-name>/CONTEXT.md`. Если его нет — создать после понимания структуры сервиса (по шаблону `docs/SERVICE_CONTEXT_TEMPLATE.md`).
5. Просмотреть `docs/PENDING.md` — возможно, задача уже описана как known gap, или связана с blocked PEND-записью.
6. Прочитать `.cursor/rules/earflow-ui-client-prefs.mdc` — **всегда** при UI/frontend; при любом «костыле» или втором control path — `INV-ARCH-001`, `INV-FE-006..008`; grep `DECISIONS` по `escape hatch`, `miniPlayStyle`, `miniBarVariant`.

## После выполнения изменения

1. Если изменение **архитектурное** (меняет публичный API сервиса, схему данных, ownership, контракт между сервисами) — добавить запись в `docs/DECISIONS.md` (формат из шаблона в начале файла).
2. Если изменение **закрывает** запись из `docs/PENDING.md` — удалить запись из PENDING и упомянуть в DECISIONS.
3. Если изменение **вводит новое правило** (после регресса) — добавить инвариант в `docs/ARCHITECTURE_INVARIANTS.md` с конкретным "красным флагом".
4. Если изменение **меняет** API/owns/caveats сервиса — обновить соответствующий `CONTEXT.md`.

## Бюджет токенов

| Что читать | Когда | Примерный объём |
|---|---|---|
| `AGENTS.md` | всегда | ~1500 токенов |
| `docs/ARCHITECTURE_INVARIANTS.md` | всегда | ~1500 токенов |
| `docs/DECISIONS.md` (через grep) | при архитектурной задаче | ~500 токенов на запись |
| `backend/<service>/CONTEXT.md` | при работе в сервисе | ~1000 токенов |
| `docs/PENDING.md` (через grep по области) | перед добавлением фичи | ~500 токенов |

**Итого baseline: ~3000-5000 токенов** для полного понимания контекста на любую задачу.

Не читать без необходимости:
- `docs/earflow-architecture-map.md` (66 KB) — только если задача спрашивает архитектурный обзор всей платформы.
- `reports/SERVICE_MAP.md` (25 KB) — только если нужно найти владельца неизвестного endpoint.
- `reports/SECURITY*.md` — только для security-задач.
- `reports/AUDIT*`, `reports/ARTIST_ANALYTICS_AUDIT*` — только если задача в той области.

## Anti-patterns (что НЕ делать)

- ❌ Начинать кодинг без чтения `ARCHITECTURE_INVARIANTS.md` — это причина 80% наших регрессов.
- ❌ Добавлять `TODO`/`FIXME` в код — для этого `docs/PENDING.md`.
- ❌ "Залатать race ещё одним useEffect/guard/ref" — если костыли копятся, **остановись** и предложи rewrite (см. `AGENTS.md → AI Discipline`).
- ❌ Создавать новые `*.md` в корне репо или в случайных местах — вся проектная документация в `docs/`, `reports/`, или `<service>/CONTEXT.md`.
- ❌ Добавлять imperative DOM paint / override CSS для UI prefs без PEND, DECISIONS и **сообщения пользователю** в том же ответе (`INV-FE-008`).
